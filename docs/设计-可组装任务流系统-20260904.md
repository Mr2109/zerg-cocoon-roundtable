## 〇、源码调研结论（v2 新增——可借鉴/不借鉴逐项判定）

### 0.1 三家架构一句话

- **graphon**（Dify 图引擎本体）：`Graph`（节点+边+拓扑）→ `GraphEngine`（事件驱动执行循环 Generator[GraphEngineEvent]）→ `VariablePool`（二级字典 selector=(node_id, name)）→ `Node[T]` 基类（`_run()` 抽象 + NodeData pydantic 自校验 + version + retry/error_strategy 声明）
- **Dify 应用层**：node_factory 注册表（NodeType→class 映射，lazy 加载）+ human_input 人在环（form 提交→PauseReason→暂停/恢复）+ DSL importer（YAML→Graph plan，装载期校验 unsupported 节点）
- **n8n**：INodeType 自描述（description+execute）+ 执行引擎（nodeExecutionStack 栈推进 + **waitingExecution 多输入汇聚等待** + 断点恢复）+ **AI Workflow Builder**（Planner/Supervisor/Builder 多代理 + validate-loop 生成-校验-修复循环）

### 0.3 明确不借鉴（过度工程判定）

| 不借鉴 | 理由 |

| Dify 11 容器部署栈（Redis/Weaviate/Celery…） | 单人本地单机——rusqlite+进程内线程足够（已如此） |

| n8n Queue 模式（Bull/Redis 分布式执行） | 单机串行引擎——本机就够，远期集群靠虫族 fleet |
| graphon 事件流 Generator 全家桶（20+ 事件类型） | 圆桌派引擎同步推进+落库——不需要事件总线，日志系统已覆盖观测 |
| 版本化节点多版本共存（IVersionedNodeType） | 单机自控——版本变了改声明即可，无需运行时多版本 |

### 0.4 关键差异确认（Mr2109核心关切）

**「他们是人搭流程，圆桌派是 AI 搭模块」的落地态**：

| 层 | 人（手动） | AI（自主） | 共用机制 |
|---|---|---|---|
| 模板声明 flow.json | 手写 JSON（grep-able） | validate-loop 生成 | **同一 schema 同一装载器**——人写的和 AI 生成的走完全相同的校验与执行路径，无特权通道 |
| 流程规划 | 直接写/改 JSON | **圆桌讨论出方案**（Plan Mode） | 讨论产出=结构化 plan（节点清单+连接+理由）→ 人确认 → 转 JSON |
| 节点参数 | UI 表单/JSON 编辑 | 讨论块由模型自决（投票/确认） | 节点级 `human_gate` 开关：AI 全自动跑 / 每步人确认 / 仅关键点确认——三档由模板声明 |
| 运行干预 | 停止/暂停按钮 | 引擎自动重试（RtError 分类） | 日志对话框同看（AI 与人的操作都进 errors/日志） |

即：**AI 与人在同一份 flow.json、同一个装载器、同一个执行引擎上会合**——不是两套系统。

## 二、A 案（模板声明文件化——内容对齐 v1，按 v2 升级）

- flow.json schema **不变**（v1 第三节）——变量引用语法升级 `{{节点id.字段}}`
- 装载器升级：serde 解析 → **schema 校验 → 变量引用校验 → 图校验**（环/悬空引用）——错误清单一次性返回（对齐 graphon importer `_unsupported_node_reasons` 风格）
- ProjectTemplate 去 static 化 + novel.flow.json 双轨对齐测试（同 v1）
- flow_vars 表结构升级：`(sid, node_id, key, value, ts)`——写入点=节点锁定时；讨论流全文投喂保留为兜底
- 节点声明加 `human_gate: none|key_points|every_step`（默认 none——现有全自动不变）

## 三、B 案（四类节点——补充 v2 增量）

- trait `RtFlowNode`（借鉴 graphon Node 基类）：
  ```rust
  trait RtFlowNode {
      fn kind(&self) -> &'static str;                 // discussion/single/tool/gate
      fn version(&self) -> u32;
      fn execute(&mut self, ctx: &mut FlowCtx) -> Result<NodeOutcome, RtError>;  // FlowCtx=变量池+会话上下文+db
      // 错误策略声明（对接 RtError：Env retryable 自动重试次数/退避）——默认继承，节点可覆写
      fn retry_policy(&self) -> RetryPolicy { RetryPolicy::default() }
  }
  ```
- 四类节点（同 v1 4.1 表）+ `gate` 节点 `human_confirm` 模式（借鉴 Dify HITL：执行到此暂停→状态置 awaiting_human→UI 确认卡→批准/驳回/改字段→恢复。驳回可 `back_to` 回跳指定节点）
- 受控 DAG（同 v1 4.2）+ 汇合预留：若未来有多输入节点，按 n8n waitingExecution 模式（记录每路已到数据，最后一路到达触发）——本期不做，设计留痕
- 模型分级（同 v1 4.3）

## 四、C 案（画布 + AI 建流——v2 重心调整）

C 不只是人的画布——**AI 建流回路是 C 的一半**（Mr2109核心关切的落地）：

### C-1 只读画布（人看）
- egui 画布渲染 flow.json（节点框/连线/human_gate 标记）——拓扑分层布局

### C-2 AI 建流回路（AI 建）——借鉴 n8n Builder，圆桌派化
1. **规划=圆桌讨论**（招牌复用）：用户需求进讨论引擎，角色团围绕「流程该怎么走」讨论产出结构化方案（节点清单/每节点职责/连接/门禁点）——讨论本身就是流程质量的第一道群策把关
2. **确认卡**：方案以 Mermaid 图+人话步骤展示（借 n8n Mermaid 中间表示——省 token 且人可读）——人改/确认
3. **生成+validate-loop**：确认后生成 flow.json → 装载器全量校验 → 错误清单回喂模型修复 → 循环至通过或达上限（MAX_VALIDATE_ATTEMPTS=5）——**人与 AI 走同一装载器，无特权通道**
4. 入库 templates/ 目录立即可跑

### C-3 编辑+模板库（人改/共用）
- 画布拖拽/连线/属性面板编辑→写回同一 flow.json
- 模板库：列表/复制/删除/导入导出——AI 生成与人手写的混存同列

### C-2+ Skill=建流知识源（2026-09-04 Mr2109提出——定案写入）

**核心命题**：网络上大量 skill（Claude Code skills/虫族 skills/行业方法论文档）本质是**人类沉淀的任务分解知识**——正是 AI 建流缺的「思路层」。三者关系：

- **Skill = 思路层**（合同怎么拆维度/评审防什么坑/验收什么格式——方法论资产）
- **节点词汇表 = 结构层**（discussion/single/tool/gate——引擎能力，AI 只组合不发明）
- **validate-loop = 校验层**（组合对错可判定）

AI 建流 = **skill（思路）× 节点词汇表（结构）× validate-loop（校验）**——缺 skill 建流只能拼出平庸流程，n8n 已实证此路径（其 Planner 代理第一步即检索 best practices 文档库——27 个 technique 文档）。

**粒度映射**（skill 几乎是 flow.json 的自然语言前身）：skill 的「怎么拆维度」→ 角色团设计；「注意什么坑」→ discussion 节点 desc 引导文案；「输出什么格式」→ fields/gate 规则；「可执行脚本/工具」→ tool 节点。

**落地三件事**：
1. **检索注入**：建流规划讨论的上下文组装加一步——按需求关键词检索 skill 库（虫族 skills + 未来收的网络 skill）注入讨论——角色团在「方法论证据」上辩论流程结构，不空想（复用 kb_* 体系）
2. **入库闸门**：网络 skill 质量参差且多为特定运行时格式——能迁移的主要是「思路」部分——套虫族 Skill 进化机制（候选试跑→成功转正/失败作废），不照单全收
3. **进化闭环**：flow 跑出的经验（哪些门禁卡得好/哪个角色配置有效）沉淀回 skill 库——「知识库→SKILL.md→CA 加载→新经验」链复用——**skill 库与 flow 库互相喂养=自举**

## 六、风险与回滚（v2 增量）

- **AI 生成质量**：validate-loop 是硬闸（schema+引用+图三重校验）——AI 最多 N 次修复，过不了就给人看错误清单人接管——永不静默入库坏流
- **AI 建流成本**：规划是一次圆桌讨论（数轮 LLM）+ 生成修复循环——本地模型零现金成本，时间可控（讨论引擎已实测速率）
- 其余同 v1 第七节（主循环改造等价性专测/变量池膨胀/回滚策略）

## 七、确认项定案（2026-09-04 Mr2109答复+深度调研）

### 7.1 角色团规模可选（Mr2109）

- 模板 `roles.panel` 为**变长列表**（1-8 个角色）——不再锁死 5 作者；角色描述/专长由模板声明
- 讨论/投票状态机按 panel 实际数量推进（n 选一投票等逻辑全数量无关）
- 小说模板 5 作者不变；新模板按任务配角色

### 7.2 validate-loop 上限——定 10（Mr2109授权调研，我定案）

**调研结论**（n8n 源码 + 业界实践）：
- **n8n 实际值**：`MAX_VALIDATE_ATTEMPTS = 10`、`MAX_AGENT_ITERATIONS = 50`（ai-workflow-builder.ee/src/code-builder/constants.ts:11-13）——v1 设计写的 5 偏保守
- 业界三层防线共识（ingramhaus/lambdaflux 2026）：**max turns 硬上限 + 超时 + 重复检测**（同一动作连续 3 次即熔断）——光有次数上限不够，还要防「10 次犯同一个错」
- **圆桌派定案**：
  - `MAX_VALIDATE_ATTEMPTS = 10`（对齐 n8n——生成修复循环）
  - `MAX_AGENT_ITERATIONS = 50`（整个建流回路硬顶）
  - **重复指纹检测**（复用引擎 LoopGuard 思想）：连续 3 次校验错误清单无变化→提前熔断（「AI 在死磕同一个错」早停，省时省 token）
  - 熔断后不静默：错误清单+已生成半成品入 errors 表+UI 呈现，人接管

### 7.3 human_gate 默认全自动 none——确认（调研佐证）

**调研结论**（stackai/scalekit/mindstudio HITL 模式 2026）：
- 业界共识是 **human-on-the-loop 优于 human-in-the-loop**：默认自动跑，异常时升级给人（置信度低于阈值/高风险不可逆动作/循环不收敛三信号触发升级）——而不是每步等人
- gate 模式调研佐证：Pause-Resume Interrupt（LangGraph interrupt()）是标准机制——全状态快照持久化后暂停，人答复后恢复——与我们断点续跑机制天然同构
- **圆桌派定案**：默认 none（全自动）正确；`human_confirm` 的暂停实现直接挂到现有断点续跑存储上（暂停=落库 awaiting_human+复位，恢复=确认后续跑）——零新增持久化机制
- 升级信号接 errors 表：Env 重试耗尽/质量评分连续 D 级→自动建议插入 human_gate（人审点）——AI 流程自我保护

### 7.4 B4 第二任务流——定「合同审查」（调研定案，待Mr2109最终拍板）

**调研结论**（多源交叉）：
- **合同审查是多智能体的教科书场景**（2026 多篇生产指南一致引用）：任务天然分专业维度——法务合规/商务条款/财务条款/知识产权——各维度独立审查再汇总；单智能体长上下文会漏条款（注意力稀释），正好是圆桌派「分角色群策」的主场
- 多智能体辩论研究佐证：辩论式审查比单裁判与人类判断相关性提升 10-16%（Du 2023/ChatEval 系）；**批评-修改循环两轮最优**（超过两轮趋向共识化而非改进）——门禁重跑上限 2-3 次的现有设计得到实证支持
- 用户真实场景匹配：Mr2109有乙方合同审查既有工作流（红删除线/红字/蓝字法律依据——民法典 585/566/497 引用格式已成惯例）——产出格式有真实标准可对照，验收不虚
- 与小说流差异度大：用到 tool/single 节点（合同文本抽取）、专业角色团（非创作者角色）、human_confirm（法务确认）、结构化字段——**把 A/B 案新能力全部用一遍**，实证价值最大

## 九、虫族 × 圆桌派：多模态时代的任务引擎（战略层——2026-09-04 Mr2109命题）

### 9.1 两个系统的本质分工

- **圆桌派 = 大脑皮层（决策器官）**：群策讨论产出「决定」——做什么、怎么拆、标准是什么、哪个方案好。输入输出以**文本/结构化数据**为主。
- **虫族 = 全身（执行器官+算力池）**：zerg-core 网关调度全设备算力（X3/M4/mini 集群），agent 执行具体动作（135+ 工具/CA 派单），模型是可替换算子（fleet 适配器）。
- **对接面天然存在**：圆桌派的 provider 就是虫族网关（8082）——讨论的每个角色调用已经是虫族调度。缺的不是通道，是**节点类型**。

### 9.2 关键洞察：节点词汇表天然容纳多模态

四类节点的抽象没有一处假设「模型只输出文字」——`RtFlowNode::execute(ctx) -> NodeOutcome`，产出写变量池，类型不限：

| 未来模型 | 落为节点 | 任务流示例 |
|---|---|---|
| 音乐模型（ACE-Step 类） | `tool` 节点（调虫族音乐服务） | 小说 flow 的 n6 后接「主题曲生成」——正文锁定→歌词讨论→音乐生成→试听 gate（人核） |
| 视频/图像模型（可灵/SD 类） | `tool` 节点 | 封面生成流：设定锁定→封面构图讨论→图像生成→评分 gate 重跑 |
| 语音模型（VoxCPM/TTS） | `tool` 节点 | 有声书流：正文→台词提取讨论→角色音色分配讨论→逐段合成→试听修正 |
| 文字模型（ornith/Qwen/DS4…） | 讨论角色/单问节点——**模型分级** | 重讨论用 ornith，抽取/总结用 Flash 档——已有设计 |
| OCR/ASR | `tool` 节点 | 合同审查的输入端：扫描件→OCR→结构化；会议录音→ASR→纪要审查流 |
| 虫族 CA（agent 执行体） | `tool` 节点（派单） | 「讨论定方案→CA 写代码实现→测试结果回流→评审讨论再定」——软件工程任务流 |

**范式一句话**：讨论节点决定「做什么/好坏标准」，工具节点让「任何模态的模型」执行，gate 节点把人拉进来把关——**圆桌派是各种本地模型的指挥所，虫族是弹药库**。

### 9.3 为什么这个结合是虫族独有的（护城河）

1. **本地+私域**：合同/剧本/未发布小说——不能上云的任务，云 SaaS 编排（n8n cloud/Dify SaaS）直接出局
2. **算力即节点**：虫族 fleet 加机器=加并发讨论槽/加模型档位——任务流引擎与算力池同源生长（单槽串行/设备级并行的既定经验直接适用）
3. **群策是招牌**：市面 workflow 引擎全是「单 LLM 节点+连线」——多角色辩论+投票+门禁重跑是圆桌派独有节点，且已被多智能体研究实证提质（10-16%）
4. **进化闭环**：skill 库↔flow 库互相喂养（C-2+ 节）+ 虫族资源信任度体系（🆕→✅）——流程本身也是资源，跑得多→转正→推荐

### 9.4 实施衔接（不新增大项——挂进现有清单）

- **现在（A/B 期）**：`tool` 节点预留 `dispatch` 形态（调虫族 agent 派单 API——zerg-core /api/tasks 已有）——B3 的 tool 节点最小集先做 HTTP+脚本，dispatch 形态接口留位
- **B4 合同审查**：输入端实测一个 tool 节点（合同文本文件读取/OCR 预留）
