# 设计——圆桌派全面日志系统与报错体系（v1——2026-09-04）

> 仓：zerg-cocoon/圆桌派（zerg-roundtable）——状态：**草案待Mr2109确认**
> 依据现状实测：9 处 eprintln/println 散点、159 处 unwrap/expect、engine 层 Result<_, String> 错误无结构、log/env_logger 已在 Cargo.toml 但**零使用**、UI 仅一个 self.err 字段（一次性、会被覆盖、无历史）

---

## 一、现状问题（实测定位）

1. **日志无分级、无落盘**：9 处 eprintln 直接打 stderr，跑完就丢——问题复盘只能靠猜。`log`/`env_logger` 依赖已声明却从未 use。
2. **错误无体系**：engine 全层 `Result<_, String>`（12 处）——错误没有分类（可重试？用户操作错？系统故障？）、没有上下文（哪个会话/哪个 Block）、没有汇总。AI 层有 `AiError`（Api/Http/Parse/Empty 四类）是唯一像样的，但只覆盖 AI 调用。
3. **159 处 unwrap/expect**：DB 层 48 处、engine 层 77 处——任何一处 panic 整个 UI 进程死掉，引擎线程死掉后 DB 还残留 running（今天 rt_6a9980e8 就是这样被部署 pkill 杀的——已有 reset 兜底，但 panic 路径没有）。
4. **UI 无错误呈现**：self.err 单字段，新错误覆盖旧错误，用户看不到发生过什么；引擎后台线程的失败只在 log 里，UI 状态却显示 idle，像什么都没发生。
5. **AI 调用无观测**：token 用量有 token_usage 表，但每次调用的耗时/重试次数/失败原因没有记录——「仙侠复仇记跑到 Block 4 很慢」这类问题无法定位。

## 二、设计目标（按优先级）

- **G1 不丢**：所有引擎/AI/DB 关键事件落文件 + DB 双通道，重启后可查。
- **G2 分类**：错误分四类（用户错/环境故障/系统 bug/AI 质量问题），各类处理策略不同——环境故障自动重试不消耗任务重试次数（对齐虫族故障自愈铁律）。
- **G3 可见**：UI 有日志面板（会话内可看本会话日志/错误），失败状态上状态灯，不再「像什么都没发生」。
- **G4 不炸**：unwrap 治理分三档，引擎主循环内禁裸 unwrap。
- **G5 轻量**：不引重型 APM；log + env_logger + 自写 JSONL 落盘 + errors 表，总量控制在 ~600 行新代码。

## 三、总体架构

```
┌────────────────────────────────────────────────────┐
│ UI 层（日志面板 tab / 状态灯 / 错误 toast 区）        │
├────────────────────────────────────────────────────┤
│ 日志门面 log crate（info/warn/error）               │
│   ├─ env_logger → stderr（开发可见）                │
│   └─ custom log.crate Logger → 双落盘：             │
│       文件 logs/roundtable.YYYYMMDD.log（JSONL）    │
│       errors 表（warn/error 级别镜像入库）           │
├────────────────────────────────────────────────────┤
│ 业务层：engine / ai / db / ui                        │
│   - RtError 枚举（本设计新增——替换 Result<_,String>）│
│   - ? 传播 + 上下文包装（sid/block/ chapter）        │
└────────────────────────────────────────────────────┘
```

核心原则：**业务代码只管 `log::info!/warn!/error!` 和 `RtError`，落盘/入库/格式统一由 Logger 实现**（实现 `log::Log` trait——log crate 标准挂点）。

## 四、日志系统设计

### 4.1 分级与内容规范

| 级别 | 用途 | 例 |
|---|---|---|
| ERROR | 需要用户知道失败的事 | 引擎线程退出、AI 连续 3 次重试后仍失败、DB 写失败 |
| WARN | 降级/回退/可自动恢复 | provider 白名单回退、fastembed 不可用跳过、AI 重试第 2 次、质量评分解析失败用默认 C |
| INFO | 关键生命周期事件 | 会话创建/开始讨论/Block 锁定/章节生成完成/停止请求 |
| DEBUG | 开发排查 | 每轮 AI 调用耗时、检索命中数、状态机迁移明细 |

内容强制三要素：`session_id`（有会话上下文时）、`模块`、`动作+结果`。JSONL 字段：

```json
{"ts":"2026-09-04T02:30:00+08:00","level":"WARN","module":"ai","sid":"rt_6a9980e8","block":"核心冲突","msg":"AI 重试 2/3：HTTP 429","elapsed_ms":3210}
```

### 4.2 落盘策略

- **文件**：`logs/roundtable.YYYYMMDD.log`（JSONL——相对 DB 同目录，独立跑时在 crate data/，嵌入时随 DB 路径走）按天滚动，保留 30 天（启动时清理过期）。
- **DB errors 表**（新增，见 5.3）：仅 WARN/ERROR 镜像入库——UI 面板直接读表，不用解析文件。
- **写入方式**：Logger 内部一个 `mpsc::channel` + 专职写线程（文件 append + 批量入库）——业务线程只 send，不阻塞引擎（对齐 Web 版 asyncio.to_thread 教训：IO 永不卡讨论循环）。
- **启动初始化**：`RoundtableApp::new()` 里 `logging::init(db_path 所在目录)`——幂等（重复调用忽略）；RUST_LOG 环境变量控制级别，默认 info。

### 4.3 现有 9 处散点迁移映射

| 现状 | 改为 |
|---|---|
| session.rs:49 讨论完成 | info!(sid, blocks) |
| session.rs:60 引擎错误 | error!(sid, msg) + 会话 status=failed |
| session.rs:83 provider 回退 | warn! |
| mod.rs:102 DB 打开失败 | error!（初始化失败允许 panic——无 DB 无法运行） |
| mod.rs:141 running 复位 | info! |
| embedder.rs:107 / memory.rs:195 fastembed 跳过 | warn! |
| zerg.rs:254 真调回复 println | 删（debug! 摘要 100 字替代） |
| quality.rs:113 评分告警 | warn!(block, 前200字) |

## 五、报错体系设计

### 5.1 统一错误枚举 RtError（engine/db/ai 三层通用）

```rust
pub enum RtError {
    /// 用户操作错——不重试，UI 提示改操作
    User(String),            // 例：主题为空、模板字段锁定仍提交
    /// 环境故障——自动重试/挂起，不计任务失败（AI 429/超时/DB busy）
    Env { what: String, retryable: bool },
    /// 系统 bug——不重试，ERROR + 建议报 bug
    Bug(String),             // 例：状态机非法迁移、锁中毒
    /// AI 质量问题——门禁重跑路径（评分 D 级、解析失败）
    AiQuality(String),
}
impl std::error::Error for RtError {}
```

- **分类决定处理**：`Env{retryable:true}` → 引擎自动退避重试（现有 zerg.rs 重试逻辑收编）；`User` → UI 蓝色提示；`Bug` → UI 红色 + 写 errors 表；`AiQuality` → 走 quality_check 现有 D 级重跑路径。
- **上下文包装**：错误向上传播时统一带位置——`map_err(|e| RtError::ctx(e, "block:核心冲突/phase:讨论"))`——errors 表存完整链。

### 5.2 迁移策略（不动语义只换壳）

12 处 `Result<_, String>` → `Result<_, RtError>`：engine 7 文件 + db/crud 涉及处。原 String 错误内容全部归入 `RtError::Bug` 或按实义归类；`AiError` 保留（AI 层内部细节），在 zerg.rs 出口处映射为 `RtError::Env/User/AiQuality`。
**159 处 unwrap 分三档治理**：

| 档 | 范围 | 处理 |
|---|---|---|
| A 必改 | 引擎主循环（run.rs/discussion.rs/scheduler.rs 循环体内）+ AI 调用路径 | unwrap→`?`+RtError 或带日志的降级——**panic 会让 DB 残留 running** |
| B 应改 | db 层（pool/crud） | lock 中毒→RtError::Bug；入参校验→User |
| C 暂留 | 测试代码、new() 初始化（无 DB 无法运行）、`block_on` 建库 | 保留（panic 合理——初始化失败本该退出） |

### 5.3 errors 表（DB 新增第 13 张表）

```sql
CREATE TABLE IF NOT EXISTS errors (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,              -- ISO8601 本地时间
  level TEXT NOT NULL,           -- WARN/ERROR
  module TEXT NOT NULL,          -- engine/ai/db/ui/embed
  sid TEXT,                      -- 会话上下文（可空）
  block TEXT,                    -- Block 上下文（可空）
  kind TEXT NOT NULL,            -- user/env/bug/ai_quality
  code TEXT,                     -- 细分码（见 5.4）
  msg TEXT NOT NULL,             -- 人话描述
  detail TEXT                    -- 错误链/堆栈摘要/原始返回片段
);
```

### 5.4 错误码段（code 字段——查错先看码）

| 段 | 含义 | 例 |
|---|---|---|
| U1xx | 用户操作 | U101 主题为空 U102 字段锁定 |
| E1xx | 环境 | E101 AI 超时 E102 HTTP 429 E103 DB busy E104 fastembed 缺失 |
| B1xx | 系统 | B101 状态机非法迁移 B102 锁中毒 B103 JSON 解析失败 |
| Q1xx | AI 质量 | Q101 评分 D 级 Q102 草案解析失败 Q103 回复为空 |

错误码在抛出点常量定义（`pub const E102_HTTP_429: &str = "E102";`），避免魔串。

### 5.5 UI 呈现（三层）

1. **状态灯**：会话顶栏状态扩展——running 绿/failed 红/stopped 黄（failed 新增——引擎退出码非正常时置位，替代现在「失败像没发生」）。
2. **错误 toast 区**：UI 底部固定条，`RtError::User` 蓝色可自动消失；`Bug` 红色常驻需手动关；点击展开 detail。
3. **日志面板**：SessionView 右栏加「日志」tab（与模板字段并列）——读 errors 表 WHERE sid=? ORDER BY id DESC LIMIT 200，每行 `时间 级别 码 消息`，可复制。
